# First chapter: progression transaction contract

The three nodes are ForestCourt (0, 林庭复明), Redrock (1, 赤岩断供), and StarPlatform (2, 星台封印). Each contains two rooms: Purify→Escape, Hunt→Escape, Rest→Boss. A normal completion unlocks the next node and that node's Hard difficulty; Hard unlocks Heroic on the same node. Completed nodes remain independently replayable. Difficulty never raises the authorized adventure tier.

`TryBeginChapterNode(node, difficulty, tier, out receipt)` validates the active save, chapter and difficulty gates, and tier ≤ min(100, highest adventure tier + 1). It fixes the node/difficulty/tier/reward in an immutable receipt. Begin failure leaves the earlier valid attempt intact. A successful new begin replaces that attempt. Host code owns the actual two-room completion evidence and world epoch; it calls `CancelChapterRun()` on abandonment. Reloading or creating a character also cancels an uncommitted attempt.

`TryCompleteChapterNode(receipt)` clones the current profile and commits chapter completion, best difficulty, first-reward mask, material payout and dedicated receipt in one existing save transaction. Failed disk writes publish neither a replacement profile nor a Changed event; the same receipt remains retryable. The last committed receipt is idempotent, including after reload. A previous sequence or superseded attempt cannot reward again. The stored monotonic sequence keeps this protection bounded without retaining an unbounded GUID list.

Base materials are 1/1/2, using the existing tier band. Each node's first completion adds exactly one unscaled fragment; Hard/Heroic add no multiplier. UI and host use `ChapterProgression.CompletionMaterials(profile,node,tier)` for the same total as the receipt. Gold/drop formulas remain unchanged; XP follows the fixed entry-level chapter budget. Forest and Redrock do not grant shared first-core eligibility; completing Star Platform finishes the chapter and enables the existing one-time claim, without resetting its shared claimed flag. Chapter completion does not grant an ordinary dungeon counter or fashion chest.

Only a completed StarPlatform advances shared highest adventure tier. `chapterHighestAdventureTier` and `chapterPriorAdventureTier` distinguish its contribution from older modes during the existing ValidateProfile path. Existing pending first-clear evidence is preserved, so an ordinary mode completed at tier 1 after chapter tier 5 still grants its original qualification. This prevents normalization from inventing a global core solely from chapter progress. Existing profile version remains 1; absent chapter fields mean no chapter progress, regardless of prior highest tier. JSON snapshots naturally copy all new fields and arrays.

Validation: `Tests/ChapterProgressionTests.py <dotnet-path>` runs actual ProgressionService saves with managed JSON transport and real temporary files. It covers chapter, mode-reward and shared progression rules. Mandatory mutations restore the old highest-tier inference and admit an old receipt after a newer settlement; each must fail the production test. This is not Unity engine, map, combat, GPU or device acceptance.

For every existing standalone test compiling ProgressionService.cs, add ChapterProgression.cs, ProgressionService.Chapter.cs and RoomTactics.cs, deduplicating existing sources. The standalone chapter Python check explicitly supplies its dependencies; Tools/cloud-validation.py registers the reusable check.
